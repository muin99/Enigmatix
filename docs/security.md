# Security review, threat model, and vulnerability register

Assessment date: 2026-10-25. Evidence reviewed: the original Markdown blueprint and the revised architecture. There is no application code, deployed backend, dependency inventory, or binary to audit. The items below are design risks and verification requirements, not confirmed exploitable code findings. This cannot establish that all vulnerabilities have been found.

## Assets, attackers, and limits

Assets: plaintext, private keys, passphrases, recovery exports, session state, contact identity bindings, payment rights, credit balances, and metadata. Attackers include malicious transport apps, hostile ciphertext senders, network adversaries, a compromised directory/backend, account thieves, dishonest clients, malicious dependencies/updates, and future quantum-capable adversaries.

Trust boundaries: sensitive input to app memory; JS to native core; extension to vault; device to directory; app to store/backend; user to recipient; CI to signed release. Fully compromised OS, malicious client release, unlocked physical access, privileged recording, and a recipient forwarding plaintext remain outside the confidentiality guarantee. Root/jailbreak signals are advisory and bypassable. Host apps already exposed to plaintext cannot be made to forget it.

Intended claim: the operator lacks sufficient server-side material to decrypt messages generated by verified clients using user-held keys. TLS and encrypted databases protect other boundaries; neither replaces E2EE. Metadata remains observable. A client supply-chain compromise can defeat this claim at the endpoint.

## Prioritized design risks

Severity expresses potential impact if controls fail. Owner roles must be assigned to named maintainers before implementation.

| ID / priority | Attack or failure | Required control | Evidence / owner |
|---|---|---|---|
| S01 Critical | Plaintext leaks via host input, JS logging, third-party keyboard, telemetry | Isolated native composition, minimal data paths, no text telemetry | Host/IME/leakage tests; mobile lead |
| S02 Critical | Directory substitutes recipient keys | QR verification, signed updates, key-change blocking; later transparency | Malicious-directory simulation; crypto lead |
| S03 Critical | Custom hybrid construction or downgrade | Reviewed protocol, transcript binding, allowlisted suites | Protocol review and downgrade tests; crypto lead |
| S04 Critical | Nonce/key reuse after crash, restore, or concurrent send | Atomic session state, serialized mutation, safe recovery/new sessions | Fault injection and rollback tests; crypto lead |
| S05 High | Weak phrase guessed offline | Generated phrases, Argon2id floor, honest warnings | Cost benchmarks and UX tests; crypto/mobile |
| S06 High | Malformed envelope/KDF parameters exhaust memory or exploit FFI | Size/work caps before allocation, safe parser, native boundary review | Fuzzing and malformed corpus; crypto lead |
| S07 Critical | Account recovery becomes key escrow or identity takeover | Separate account/key recovery; user-held exports; trusted enrollment | Reset/lost-device/red-team scenarios; security lead |
| S08 High | Backup, screenshot, notification, clipboard, or crash dump leaks secrets | Backup exclusions, app-switcher redaction, private notifications, opt-in clipboard | Physical-device forensic checks; mobile lead |

| S12 High | Prekey exhaustion or replay confuses sessions | Atomic one-time prekey handling, rate limits, protocol replay rules | Duplicate/prekey depletion tests; crypto/backend |
| S13 High | Cross-device cloning reuses ratchet state | Reviewed device protocol; no casual state cloning | Enrollment/revocation tests; crypto lead |
| S14 High | Billing outage/expiry traps user data | Local decryption and key export independent of entitlement | Offline/expiry/refund tests; product/mobile |
| S15 High | Wallet/public chain creates identity graph or relies on vulnerable signatures | No default wallet; no personal/on-chain message data | Privacy and chain-dependency review; security lead |

Clipboard timeout is best effort: other apps may retain copies. Screenshot protection is platform-dependent and cannot stop an external camera. Biometrics gate local access but are not a peer authentication protocol. Generic decryption failure avoids an oracle; detailed diagnostics must remain secret-free.

## Service and privacy controls

TLS for APIs; authenticated authorization independent of UI checks; bounded requests and rate limits; safe SQL queries; SSRF protection if any server fetch exists; no arbitrary envelope-provided URLs. Separate directory keys from entitlement signing keys. Rotate backend secrets and test backup restoration. Avoid publishing complete contact graphs. Define retention by data category before launch: financial records, directory history, encrypted objects, device/account records, security logs, and deletion requests. Do not claim zero metadata or zero retention until demonstrated.

Cloud sync encrypts and authenticates objects client-side with a dedicated key domain. The backend still sees object sizes, timing, accounts, and IPs. Prevent stale rollback where possible; document cross-device consistency. Do not sync raw ratchet databases as ordinary settings. Account deletion removes eligible service data under defined retention obligations; it cannot delete recipient copies, public chain records, or third-party transport history.

## Verification and release gate

Map requirements to OWASP MASVS categories: STORAGE, CRYPTO, AUTH, NETWORK, PLATFORM, CODE, RESILIENCE, PRIVACY. Maintain requirement → test → evidence → owner → residual risk. Use MASTG procedures where applicable. Passing an automated scanner is not a cryptographic audit.

Before public encryption release require protocol design review, native/FFI and mobile pentest, cross-platform vectors, parser fuzzing, supply-chain review, and physical-device tests. Before paid release add store sandbox/adversarial billing checks, cross-account authorization tests, reconciliation and restore drills. Fix all critical/high findings or keep the affected feature disabled; record and approve remaining risks explicitly. Publish audit scope, version, date, and unresolved limitations rather than claiming universally audited security.

Incident runbook: triage, reproduce safely, restrict affected online features, notify users with accurate impact, rotate service keys or initiate reviewed device rekey as appropriate, ship signed fixes, and publish follow-up. Security changes must preserve safe offline decryption where feasible; never silently downgrade suites. Create a security contact and coordinated disclosure process before beta. Reproducible builds are a target; document platform signing/toolchain limits and evidence instead of asserting they already exist.
